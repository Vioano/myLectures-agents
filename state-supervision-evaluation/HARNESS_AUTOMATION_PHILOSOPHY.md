# Harness 自动化哲学：保留系统复杂性，压缩实时工作集

状态：项目方向基线（2026-08-31 第二轮校准）

适用范围：数学物理动画生产、状态监督系统、后续可迁移的 AIGC 工作流

证据范围：Episode 7–12 生产复盘、八分钟状态系统演练、当前 Human/Agent interface 反馈

## 结论先行

本项目不应回退到“简单 Skill + 人工逐镜头指挥”的最终形态。那条路线可以完成作品，而且在用户已经写出极细分镜时，往往能够获得很高的审美对齐；但它把产量上限锁在人类逐镜头设计时间上，无法实现一天一集乃至多集、稳定质量和可控 token 的目标。

因此，本项目仍然需要一个足够复杂、会持续演化的 Harness。需要改变的不是复杂性的总量，而是复杂性的**位置、表示方式和消费时机**：

- 复杂性应保留在状态内核、领域编译器、工具、验证器、案例库、评估器和恢复机制中；
- 单个 Agent 在一个动作边界只接收完成当前任务所需的最小充分工作集；
- 创造性判断不应被大量微观硬规则替代，而应由强模型在清晰目标、真实素材、少量高价值案例和可验证反馈下完成；
- 稳定、可机械判断、反复出现的部分应退出提示词，进入代码、数据结构、状态约束或自动检查；
- Human UI 和 Agent API 是同一后端状态的两种等价投影，任何一端关闭或故障都不应中断生产。

一句话概括：**要建设复杂的自动化系统，而不是让每一次模型调用都背负整个复杂系统。**

## 1. 三种复杂性必须分开

### 1.1 领域任务复杂性

数学物理动画本身就是复杂任务。它同时包含：

- 数学真实性与教学因果；
- 口播、逐词时间、字幕和画面动作对齐；
- 视觉语言、构图、节奏、角色层和系列审美；
- Manim 实现、渲染、媒体合成与发布；
- 人审、独立审查、返修、后期变更和最终授权。

这部分复杂性无法靠删文档或缩短提示词消失。

### 1.2 Harness 内部复杂性

为了让复杂任务自动化并规模化，系统需要承担状态权威、并发、租约、版本、产物 lineage、局部失效、反馈投递、审查隔离、恢复、事件日志和成本治理。这部分内部复杂性不仅可以存在，而且必须继续增强。

但内部复杂性必须通过稳定接口封装。若一个制作 Agent 为了写一个场景，必须理解整套租约恢复、所有历史补丁、全部状态节点和每条审查规则，说明封装失败，而不是说明 Harness 太复杂。

### 1.3 单次注意力工作集复杂性

Agent 当前真正需要持有的是：

1. 当前目标与“为什么现在做它”；
2. 当前有效输入及其版本/哈希；
3. 与本任务直接相关的约束和人类反馈原文；
4. 可使用的能力与禁止越过的边界；
5. 成功证据、提交方式和下一道门；
6. 少量真正有帮助的案例或风格锚点。

它不应同时读取未来五个阶段的全部操作细则，也不应把任务 ID、反馈 ID 或长篇索引误当成语义本身。这里追求的是**最小充分上下文**，不是越短越好。

## 2. 人工精细分镜是一条重要基线，不是最终方向

用户可以手工规定每个函数、坐标轴、公式、镜头和动作，然后让只懂 Manim 基础的 Agent 执行。这个模式证明了两件事：

1. 高质量结果不天然依赖复杂 Skill；
2. 当视觉意图已经被用户完全指定，要求 Agent 重新探索同一方案只会浪费 token 并增加偏差。

因此，系统必须保留“精确规格执行模式”。但复杂 Harness 的价值在于把用户过去逐镜头完成的工作逐渐编译成可复用能力，让同样的质量不再要求同样的人类投入。

人工精细分镜应成为自动化系统的：

- 质量和审美对照基线；
- 可检索的高质量案例；
- 视觉语法和舞台调度原语的来源；
- 评估器校准数据；
- 自动规划失败时的可控降级路径。

复杂 Harness 是否值得，不看 Skill 有多少页，而看它相对这条基线是否真正减少了人类分钟、返修、重复上下文和 token，同时保持或提高最终质量。

## 4. 八分钟演练证明了什么，又没有证明什么

演练最终通过了路线临时切换、延迟返修、人类批准撤销/重新批准、局部下游失效、后端跨前端重启续接和黑盒 Agent 完成任务等测试。说明“统一状态权威 + 事件日志 + 局部失效 + 版本化任务胶囊”的方向是对的。

但这个微型假生产仍产生了 224 个事件、138 个命令、26 个 capsule 和 80,848 个 capsule context 字符。它还暴露了：

- 浮动检查器重渲染导致输入焦点、草稿和滚动位置丢失；
- 旧 T900 产物漂移被错误提升为当前硬阻塞，并中断 live lease；
- T900 胶囊列出 9 个人类标注 ID，却没有标注正文，Agent 被迫额外调用 `explain`；
- SSE 显示在线，但浏览器曾漏掉后端 cursor；
- 当前有效路线与旧 mission 文本发生冲突；
- 观察/评估事件会造成 review context churn。

因此这次演练证明的是**状态内核具备可行性**，不是已经证明高吞吐。它反而给出了一个重要设计警报：后台可以拥有丰富事件，但 Agent 和人类不能被迫逐个消费这些事件。需要投影、压缩、聚合和例外驱动的界面。

## 5. 应该自动化什么，应该把判断留给谁

每个工作单元按四个维度分类：

- **可判定性**：能否由代码或精确证据判断对错；
- **复用性**：未来是否高频重复；
- **创造性不确定度**：是否存在多种合理方案且依赖审美；
- **错误扩散成本**：一旦选错，是否会触发后续大规模返工。

对应策略：

| 类型 | 默认实现 |
|---|---|
| 高可判定 + 高复用 | 代码、schema、状态不变量、自动验证；退出提示词 |
| 低可判定 + 高复用 | 高质量案例检索、风格原语、偏好评估器、独立审查；避免写成绝对微规则 |
| 高创造性 + 低复用 | 交给强模型探索，必要时让用户选择；不升级为全局规则 |
| 高扩散成本 | 先做低成本、真实媒介的 probe，再冻结方案；未冻结前不进入昂贵渲染 |
| 用户已给精确方案 | 直接进入规格执行，不要求 Agent 重做创意搜索 |

硬约束应集中在真正不可妥协的边界：数学对象真实性、输入/产物 lineage、审批权限、作者/审查隔离、发布证据、不可丢失的人类反馈、可恢复状态。构图、视觉隐喻和节奏不应被大量僵硬规则预先写死；系统应给强模型更好的问题、案例、工具和反馈。

## 6. 三种生产模式应按场景混合，而不是整集一刀切

### A. 精确规格执行

用户已经给出详细分镜或场景合同。Agent 主要负责转译、实现、自查和证据生成。创作自由度低，执行确定性高。

### B. 协同设计

Agent 根据教学目标、口播和既有视觉语言提出少量候选方案；用户或主审只选择高杠杆决策，随后由系统编译成精确合同。

### C. 自主规模化生产

Agent 自动完成方案、probe、实现和独立审查；Human UI 只呈现异常、审片候选和不可逆授权。这是“一天一集/多集”的主要目标形态。

同一集可以混合三种模式。一个新颖、审美风险高的核心场景可用 B；常规推导场景可用 C；用户已经想清楚的片尾可用 A。状态机应记录 `automation_mode`，而不是强迫所有节点走同一粒度的流程。

## 7. 目标架构：复杂 Skill 应成为编译器和运行时包

### 7.1 通用状态内核

负责任务图、状态、依赖、租约、版本、artifact lineage、change impact、人类决定、事件日志、恢复和权限。这一层应能迁移到其他 AIGC 工作流。

### 7.2 数学动画领域编译器

把教学意图、口播、用户偏好、历史人审和素材约束编译为：

- scene contract；
- visual-plan search brief；
- timeline 与 attention anchors；
- Manim probe/authoring task；
- 自动检查与独立审查合同；
- 面向 Human UI 的审片包。

Skill 的核心不是让 Agent 背诵规范，而是完成这次编译。

### 7.3 可复用创作资产层

逐渐积累视觉语法、舞台调度原语、真实数学变换组件、成功场景案例、失败对照、口播—画面映射和用户偏好样本。这里才是未来质量与产量同时增长的主要杠杆。

### 7.4 模型工作层

强模型负责不确定、创造性和整体判断；便宜模型负责合同明确、可机械验证的执行。模型选择应跟任务性质绑定，而不是按固定角色永久绑定。

### 7.5 评估与演化层

机器检查负责确定性失败；独立模型负责整体语义、审美和新手视角；人类负责口味、最终质量与不可逆授权。新反馈先进入观察和候选规则生命周期，只有跨场景复发且能证明收益时才升级为稳定能力。

## 8. 精确分配注意力的正确含义

精确分配不是把模型当成什么都不懂，也不是让它一次读完所有历史。它是根据当前动作选择合适的认知支架：

- capsule 必须包含人类反馈**原文**，不能只给 ID；
- 长期稳定规则按动作边界检索，不能每轮全部重放；
- 对创造性任务，应提供目标、真实素材和少量代表案例，允许模型主动检索更多上下文；
- 对确定性任务，应提供精确输入输出合同，减少自由解释；
- 非破坏当前前提的人类反馈在安全 attention boundary 投递；只有使当前前提失效的变更才中断 live lease；
- 旧历史可以用于审计和检索，但不得未经 current-lineage 判断就成为当前 blocker。

目标不是最大控制，而是让模型在正确时机拥有足够自主性，并让错误尽早、局部、可恢复地暴露。

## 9. Main Agent、Human UI 与 Agent API 的责任边界

Main Agent 应是监督与解释控制面，而不是每条反馈的人工转述器，也不应同时承担全部生产和全部独立审查。

它负责：

- 回答“进度怎么样”“现在有什么可审”“为什么卡住”；
- 把用户自然语言操作翻译成与 Human UI 等权的后端命令；
- 观察例外、容量、目标距离和质量风险；
- 在系统无法表达新动作时登记 capability gap；
- 汇总反馈影响，但不替后端重复搬运每条正文。

人类在视频某一帧留下标注后，后端保存原文、时间/位置、目标 artifact、当前决定和投递策略；制作 Agent 在合适的下一任务边界直接收到它。Main Agent 同时收到一条压缩事件，知道发生了什么、影响哪些节点、何时投递，但不需要中断正在进行的思考去手工转述。

Human UI 的主页面应优先回答四件事：

1. 现在正在发生什么；
2. 下一步是什么；
3. 哪些事情需要我；
4. 有哪些可直接审片的文件。

其余拓扑、日志、风险、工位和恢复工具按需展开。前端只是投影；后端事件和任务状态必须独立存活，重启后从 cursor 续接。

## 10. 衡量“AI 杠杆”而不是衡量规则数量

核心北极星指标是：**在质量不下降的前提下，每分钟人类投入能产出多少分钟最终获批内容。**

建议持续记录：

- 每分钟获批成片所需的人类分钟；
- 每天获批成片分钟与集数；
- 每分钟获批成片的 raw/uncached/output/reasoning token；
- 场景首轮人审通过率与 automatic false pass；
- 进入 render 后才发现的结构性视觉重做数；
- 已知人审 `pattern_key` 的复发率；
- 从临时需求变更到恢复有效下游的时间和被作废工作量；
- Agent 为补全胶囊而额外 `explain/reread` 的次数；
- pipeline/contract repair 占关键路径和 token 的比例；
- Main Agent 被用户打断或必须人工转述的次数；
- reviewer 等候、producer 队列和真实并行利用率；
- UI 草稿丢失、cursor 漏更、历史误阻塞、重复租约等状态可靠性指标。

任何新增复杂机制都必须“付租金”：它应在后续匹配样本中减少上述至少一类成本，且不提高质量风险。只有测试通过而没有真实生产收益的机制，仍只是能力证明，不是杠杆证明。

## 11. 下一阶段优先级

1. 保留并硬化通用状态内核，修复 current-lineage、反馈正文投递、前端编辑隔离和 cursor 对账。
2. 降低 Agent API 的操作面：默认只给 best-next、最小充分 capsule、可执行 denial recovery 和一次提交入口。
3. 建立场景级 `automation_mode` 与任务分类，让精确规格、协同设计、自主生产可以混合。
4. 把投资重点从继续堆 prose rule 转向数学动画领域编译器、视觉语法原语、成功案例检索和偏好评估。
5. 对创造性场景，先由强模型做整体 visual plan 与真实 Manim probe；审查一次性给完整 blocker bundle，避免微修订螺旋。
6. Episode 13 长影子运行只观察既定系统，不在生产 Session 中热改；用真实人类投入、token、返修和质量指标判断杠杆是否出现。

## 12. 当前方向判断

本项目的 Harness 哲学与“让更强模型使用更多计算、搜索和反馈”的方向不冲突。冲突只会发生在一种情况下：把历史上的每个局部修复都变成永久微观指令，以至于模型只剩机械服从、系统也无法维护。

正确方向不是减少雄心，而是把复杂 Skill 从“巨型规则文本”升级成“可演化的自动化产品”：通用状态内核承担可靠性，领域编译器承担知识复用，强模型承担创造，验证器和审查承担反馈，人类只保留高价值选择与最终授权。这样，复杂性才会成为杠杆，而不是税。
