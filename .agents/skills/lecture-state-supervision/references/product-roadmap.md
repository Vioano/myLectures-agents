## 1. 决策

下一步既不是“先把所有底层做完，再做界面”，也不是“先把界面画漂亮，再补状态真相”。

采用 **关键人类工作流的纵向切片**：先让一条完整链路从后端真相、Agent 投递、Human UI 操作到可验证日志都可靠，再扩展下一条链路。第一条链路是：

```text
系统继续运行
  -> 主页面出现可审片提醒
  -> 人类打开媒体
  -> 输入/定位标注
  -> 批准或打回（也可撤销先前批准）
  -> 后端局部失效并选择正确投递边界
  -> 制作 Agent 收到反馈原文
  -> Main Agent 看见压缩状态
  -> UI 热更新且不丢焦点、草稿、滚动和播放位置
  -> 日志能证明每一步真实发生
```

这条切片同时逼迫状态内核和 Human Interface 对齐。只做 UI 会把不可靠状态包装得更漂亮；只做底层会继续产生用户无法验证的隐藏能力。

## 2. 当前真相

当前分支已经实现并通过自动测试的能力包括：事件溯源后端、SQLite/WAL 持久化、版本化任务胶囊、局部 lineage 失效、审批撤销与重新批准、媒体 Range 流式读取、时间/画面位置标注、反馈在 attention boundary 投递、前端 cursor 对账、历史产物误阻塞恢复、详情 DOM 的局部更新和前端重载续接。

Round 02 压力演练进一步确认：后端状态在进程重启后保持完整，但 Human UI 没有可靠地从“后端不可达”自动恢复为已对账状态；“只重启界面”也不能拉起退出的服务。并行审查还暴露出 review-context hash 会被无关 sibling 的状态变化误判为 stale。它们属于当前纵向切片的 P1 基础故障，不能用继续美化首页来绕过。

这些能力分成三类管理：

1. **自动验证通过，但仍待人类验收**：输入框焦点、草稿、滚动、折叠区、浮动窗叠层、重启续接和当前路线进度。演练中真实失败过，不能仅凭测试宣布完成。
2. **状态机制存在，但尚未产品化**：Human 审片收件箱、批准撤销入口、反馈投递时机解释、Main Agent 对等操作、风险页的人话表达。
3. **尚待建设或优化**：单主页面、引导式使用、多尺度多视角图、统一画布手势、状态流动动画、完整上下文来源编辑、Agent 并行/闲置解释和真实长影子运行。

## 3. 执行顺序

### Phase 0 — 建立不会遗失的需求与验收基线

目标：先停止“问题只存在于聊天上下文里”。

- 用稳定 ID 登记所有已知问题、依赖、状态和验收证据。
- 每项只允许处于：候选、已排期、实现中、自动验证、待人验收、已验收、长期观测或退役。
- 把八分钟演练固定为回归夹具；保留失败前和修复后的证据。
- 建立四条产品级验收旅程：审片返修、前端崩溃续接、临时路线变更、合法/非法闲置。

退出门：此前所有诉求均能在台账中找到；任何新问题可在一分钟内登记并进入排序。

### Phase 1 — P0 交互安全与运行时真相

目标：用户能正常操作，且页面故障不影响生产。

- 用真实浏览器逐项验收：textarea 焦点、输入法、选区、未提交草稿、内部滚动、折叠区、批量草稿和点击传播。
- 直播增量不得重建正在编辑的详情 DOM；只更新无冲突的字段。
- 保留媒体播放时间、浮窗位置/尺寸、详情滚动和当前节点选择。
- 前端崩溃、关闭或重启时，后端任务、租约和事件继续运行；重开后从 cursor 续接。
- SSE 在线状态必须与 cursor 对账；历史 lineage 不得成为当前硬阻塞。
- 建立浏览器级回归，而不只检查源代码中是否存在某个字符串。

退出门：连续接收 live delta 时，人类可完成一条标注；关掉并重启前端后可从同一后端状态继续；没有误滚顶、清空、焦点丢失或历史误阻塞。

### Phase 2 — Human 决定与反馈投递闭环

目标：让“看到文件—给反馈—Agent 正确消费—可追责”成为第一条完整产品链路。

- 在主界面提供“待你处理”和“可审片”收件箱。
- 媒体支持播放、时间点、可选画面坐标、单条立即提交和整集草稿批量提交。
- 明确提供批准、打回、撤销批准、重新批准；显示影响范围和将被作废的下游。
- 人类标注保留原文；短文本或问号不得被系统擅自删除，可标记为 `needs_clarification`。
- 非前提破坏型反馈在下一安全 attention boundary 投递；使当前前提失效的变更才中断 lease。
- 制作 Agent 收到原文和来源；Main Agent 收到压缩事件；两者不依赖人工转述。
- 日志绑定 event、annotation/change ID、signed capsule、投递边界、Agent 动作和 review 结果。

退出门：从浏览器提交一次“已批准后又打回”的带时间/位置反馈，正确的 Agent 在正确边界收到原文，局部返修并重新批准；整条链路可由日志复核。

### Phase 3 — 单主页面与旧交互兼容

目标：大部分时间只看一页；找不到入口时仍可直接问 Main Agent。

- 主页面固定回答：正在发生什么、下一步是什么、什么需要我、哪些文件可审。
- 用异常和行动驱动通知；点击直接进入目标操作，而不是先猜页面。
- 当前并行工作、下一释放、总体进度、阻塞和目标距离同时可见。
- 页面选择器放在顶栏并明确显示当前位置；流程、结构、工位、风险和日志成为独立页面。
- 支持“进度怎么样”“有可审片吗”“发我看”“把这个打回”等旧聊天操作。
- Main Agent 调用与 Human UI 等权的后端命令；不需要模拟鼠标点击。
- 增加首次使用引导和“带我看”模式，让 Main Agent 可按页面/节点解释。

退出门：用户不切页即可回答四个主问题并完成一次审片；同一操作通过网页或自然语言产生等价后端事件。

### Phase 4 — 多尺度、多视角生产画布

目标：保留 ComfyUI 式可探索拓扑，同时避免默认摊大饼和复杂线团。

- 默认按层级展开；全图只作为可选诊断总览。
- 提供交付、内容、任务、Agent、时间和风险视角；同一状态真相，不复制状态机。
- 展示未来释放计划、真实并行分叉、返修回路、路线替换、流动领取和每个 Sub Agent。
- 结构画布独立占满视口；辅助信息改为折叠层或临时覆盖层，避免全页纵向滚动。
- 所有流程图统一使用小地图、加减、适配、全屏、双指平移、捏合缩放和相同灵敏度。
- 节点单击查看详情；双击或明确展开控件显示后续子图，避免一个手势触发两种动作。
- 气泡和侧栏是同一详情的两种投影；切换控件显示当前状态，气泡可拖动、缩放、关闭和内部滚动，全屏默认气泡。
- 状态变更使用短暂边框微光和边上数据脉冲；动效表达事件，不制造持续噪声。

退出门：在一屏内看清并行与关键路径；大图可定位、缩放和恢复；详情层不压缩或遮住主要画布。

### Phase 5 — Agent 编排与注意力产品化

目标：系统不仅知道状态，还能解释为何某个 Agent 此刻工作或闲置。

- 展示完整计划、Ready Pool、容量、实际占用、最佳下一任务和并行上限。
- 区分合法等待、非法闲置、有效工作、空烧 token 和用重复任务伪装忙碌。
- meaningful progress 必须减少目标距离；日志、缓存或重复证据不能冒充进展。
- 任务以 `work_key` 和证据身份去重；Agent 只领取能力匹配且未完成的最佳任务。
- 角色 roster 稳定复用；作者与独立审查容量分开。
- 任务胶囊只包含最小充分工作集，并显示来源：稳定规则、继承规则、临时追加、局部修改、完整重写和运行时事实。
- 用户可查看最终有效上下文、摘要、原文件路径、版本/哈希和组合顺序。
- 按任务确定性、创造性和错误扩散成本选择模型与 `automation_mode`。

退出门：盲测 Agent 不读实现文档即可完成任务；人类能解释每个 Agent 为何工作、等待或被判异常；没有重复劳动维持“看起来不闲”。

### Phase 6 — 风险、恢复与运维信任

目标：把调试页改成可理解、可预览、可恢复的操作面。

- 默认用“发生了什么—当前影响—建议动作—不会影响什么”表达。
- 当前生产阻塞、历史审计发现和 Agent 健康信号分栏，不混成同一种红色故障。
- 扫描和核验只读；修复必须先显示范围、依据、幂等键和回退方案。
- 使用产品内确认界面，不用原生 `window.confirm`。
- 所有恢复都有事件、前后状态、当前 lineage 和重放/回滚证据。

退出门：不了解内部分类名的人能判断是否需要修复、修复哪一处以及为何安全。

### Phase 7 — 视觉、可读性和性能收束

目标：在交互和状态都稳定后，统一成一个长期可用的监督产品。

- 借鉴 Archify 的架构图层次、对齐、留白、线条语义和局部聚焦，不照搬全图平铺。
- 统一字号、密度、颜色语义、状态动效、控件图标和键盘/触控可达性。
- 支持字号/画布缩放；长上下文用前段摘录、结构摘要和原路径。
- 对大型拓扑、长事件流和 4K 媒体做性能预算与降级策略。

退出门：关键页面在常用屏幕尺寸无需全页滚动；信息密度高但主次明确；动效不会掩盖真实状态。

### Phase 8 — Episode 13 长影子运行与演化

目标：证明系统带来生产杠杆，而不只是功能完整。

- 生产 Session 使用冻结版本，只记录自然发生的问题，不边生产边改系统。
- 结束后冻结事件、命令、capsule、媒体、人类反馈和成本证据，由后续评估 Session 优化。
- 记录人类分钟/获批分钟、获批分钟/天、token/获批分钟、首轮人审通过率、automatic false pass、晚期结构返工、额外 explain/reread、恢复成本和真实并行利用率。
- 新反馈经过“观察 -> 候选 -> 校准 -> 合并/退役”生命周期；不把每个局部抱怨直接追加成永久长提示词。

退出门：真实生产数据证明人类投入或 token 成本下降，且质量门没有放松。

## 4. 新问题如何插队而不打乱方向

每个新问题先登记到台账，再按以下顺序排序：

1. **P0 数据/权限/输入破坏**：丢草稿、错审批、错 lineage、前端影响后端、不可恢复，立即打断当前迭代。
2. **P1 状态真相错误**：错误阻塞、错误进度、错误投递、重复任务，在当前纵向切片内优先修。
3. **P1 主工作流不可完成**：入口找不到、审片/返修无法闭环，在当前 Phase 内处理。
4. **P2 理解与效率问题**：页面难懂、信息过载、手势冲突，排到最近相关 Phase。
5. **P3 视觉偏好与增强**：不影响真相和主任务时，进入视觉收束阶段。

旧条目不会因新问题被删除；只允许重新排序、合并重复项或明确退役，并保留原因和证据。

## 5. Round 02 之后的具体任务

Round 02 已完成“先上一次真实压力”的目的。下一步不再堆首页功能，也不立刻重复整轮八分钟剧情；按故障依赖顺序完成以下工作：

1. **修复离线/恢复状态机（U-08、U-11）**：区分界面异常、后端不可达与已恢复待对账；服务恢复后自动完成全量对账，移除无证据的“Agent 不受影响”保证，并把入口拆成“重载界面”与“重试连接”。
2. **修复并行审查隔离（K-13）**：review-context hash 只包含当前候选和任务相关事实；审批无关 sibling 不应迫使审查串行重读。
3. **校准 Agent 合同（C-11）**：任务目标、required artifact roles、提交校验和 CLI 帮助必须一致，消除盲测 Agent 对文本/WAV 必交范围的猜测。
4. **先跑聚焦浏览器夹具（U-06、M-05）**：预置一个可审 T040，固定 textarea 焦点、未提交草稿、scrollTop、折叠状态、播放时间与浮窗几何；连续注入 delta、断开 SSE、重启后端，逐项断言局部状态不变。
5. **夹具通过后再跑完整八分钟 Human 决策纵向切片**：覆盖带时间/画面位置标注、批准、打回、撤销批准、重新批准、Agent 在正确边界收到原文，以及 Main Agent/Web 等权命令。

图形化首页的现有方向保留：生产地图仍是首页主体，通知和节点角标定位同一对象，文字列表只作辅助。下一轮完整演练的开跑门不是“页面看起来更漂亮”，而是前四项有可重复证据；这样下一次八分钟才用于发现更深层问题，而不是复现已知基础故障。
